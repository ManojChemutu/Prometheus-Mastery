Core Concept

Understanding Metric Types

The four fundamental metric types in Prometheus data model

Counter: Cumulative metric that only increases (or resets to 0 on restart). Perfect for counting requests, errors, or completed tasks. Never use raw counters in graphs - always wrap with rate() or increase().

# Good: Requests per second
rate(http_requests_total[5m])

Gauge: Single numerical value that can arbitrarily go up and down. Use for temperatures, memory usage, queue sizes. No aggregation functions needed.

Histogram: Samples observations (like request durations) into configurable buckets. Provides _count, _sum, and _bucket time series. Use for SLIs and latency tracking.

# 95th percentile latency
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))

Summary: Similar to histogram but calculates quantiles client-side using sliding time windows. Higher CPU cost and can't be aggregated across dimensions. Generally prefer Histograms.

Hands-on

Installation & Configuration

Deploying Prometheus locally and in Docker

Start with Docker for local testing:

docker run -p 9090:9090 \ -v $(pwd)/prometheus.yml:/etc/prometheus/prometheus.yml \ prom/prometheus:latest

Key Configuration Parameters:

  • global.scrape_interval: How often to scrape targets (default 1m)
  • global.evaluation_interval: How often to evaluate rules (default 1m)
  • scrape_configs: Array of jobs and targets to monitor

Storage Configuration:

TSDB retention is controlled by --storage.tsdb.retention.time (default 15d) or --storage.tsdb.retention.size for size-based retention.

Querying

First PromQL Queries

Instant vectors, selectors, and basic filtering

Instant Vector Selectors: Select series at a single point in time.

# Select all http_requests_total series
http_requests_total

# Filter by label
http_requests_total{method="GET", status="200"}

# Regex match
http_requests_total{status=~"2.."}

Range Vectors: Select samples over a time range (required for rate calculations).

# Last 5 minutes of samples
http_requests_total[5m]

Time Durations: ms, s, m, h, d, w, y. Must be used in square brackets for range vectors.

Exporters

Node Exporter Deep Dive

Monitoring Linux/Unix system metrics

Node Exporter exposes hardware and OS metrics. Key collectors include:

  • cpu: CPU usage modes (user, system, idle, iowait)
  • memory: RAM usage, buffers, cache
  • filesystem: Disk usage and inode statistics
  • diskstats: I/O operations and throughput
  • network: Interface traffic and errors

Essential Queries:

# CPU Usage %
100 - (avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)

# Memory Usage %
100 * (1 - ((node_memory_MemAvailable_bytes or node_memory_Buffers_bytes + node_memory_Cached_bytes) / node_memory_MemTotal_bytes))

Best Practice: Disable unused collectors with --no-collector.XXX to reduce resource usage.

PromQL

Advanced PromQL & Aggregations

Rate calculations, aggregation operators, and vector matching

Rate vs Irate:

rate() calculates the average per-second over the range, smoothing spikes. irate() uses only the last two data points, showing instant spikes. Use rate() for alerts, irate() for dashboards.

# Request rate per minute
rate(http_requests_total[5m]) * 60

# Total increase over 1 hour
increase(http_requests_total[1h])

Aggregation Operators:

  • sum: Calculate total across dimensions
  • avg: Average (susceptible to outliers)
  • max/min: Identify hotspots
  • count: Count number of series
  • topk/bottomk: Select extreme values
  • quantile: Calculate φ-quantiles (0 ≤ φ ≤ 1)

Without vs By:

# Sum everything, keep only 'method'
sum by (method) (http_requests_total)

# Sum everything except 'instance'
sum without (instance) (http_requests_total)
Rules

Recording & Alerting Rules

Pre-aggregation and automated alerting

Recording Rules: Pre-calculate expensive queries to improve dashboard performance. Stored as new time series.

# rules.yml
groups:
  - name: api_rules
    interval: 10s
    rules:
      - record: job:http_requests:rate5m
        expr: sum by (job) (rate(http_requests_total[5m]))

Alerting Rules: Define conditions that trigger alerts to Alertmanager.

- alert: HighErrorRate
  expr: |
    sum by (job) (rate(http_requests_total{status=~"5.."}[5m])) /
    sum by (job) (rate(http_requests_total[5m])) > 0.01
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "High error rate in {{ $labels.job }}"
    description: "Error rate is {{ $value | humanizePercentage }}"

Key Concept: The for clause prevents flapping. Alert must be active for 5 minutes before firing.

Alerting

Alertmanager Configuration

Routing trees, inhibition, and silencing

Routing Tree: Alerts are matched against routes in order. First match wins unless continue: true.

route:
  group_by: ['alertname', 'cluster']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 12h
  receiver: 'default'
  routes:
    - match:
      severity: critical
      receiver: 'pagerduty'

Inhibition: Suppress notifications for lower severity alerts if higher severity is firing:

inhibit_rules:
  - source_match:
      severity: 'critical'
    target_match:
      severity: 'warning'
    equal: ['alertname', 'cluster']
Discovery

Service Discovery

Kubernetes, Consul, and EC2 auto-discovery

Kubernetes SD: Automatically discovers pods and services via the API server.

scrape_configs:
  - job_name: 'kubernetes-pods'
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: true
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_port]
        action: replace
        target_label: __address__
        regex: ([^:]+)(?::\d+)?;(\d+)
        replacement: $1:$2

Meta Labels: Special labels starting with __meta_ provided by SD mechanisms. Use relabeling to convert them to target labels.

Performance

Performance Tuning & Cardinality

Managing high cardinality and scrape optimization

Cardinality Crisis: Cardinality = number of unique time series. Explodes with high-cardinality labels like user_id, request_id, or IP addresses.

Mitigation Strategies:

  • Drop high-card labels using metric_relabel_configs
  • Use sample_limit in scrape_configs to protect against runaway targets
  • Increase scrape interval for high-volume targets
  • Shard by job using external_labels and federation
# Drop user_id label to prevent cardinality explosion
metric_relabel_configs:
  - source_labels: [user_id]
    target_label: user_id
    replacement: ''
    action: replace

Scrape Optimization:

Use scrape_timeout and scrape_interval tuning. For >1000 targets, consider horizontal sharding.

Storage

Remote Storage & Federation

Long-term storage solutions and cross-cluster aggregation

Federation: Hierarchical scraping where a global Prometheus scrapes aggregated metrics from regional Prometheus servers.

# Global Prometheus scrape config
scrape_configs:
  - job_name: 'federate'
    honor_labels: true
    metrics_path: '/federate'
    params:
      'match[]':
        - '{__name__=~"job:.*"}' # Only aggregated metrics
    static_configs:
      - targets: ['region1-prometheus:9090']

Remote Write: Stream samples to external systems (Thanos, Cortex, InfluxDB):

remote_write:
  - url: "http://cortex:9009/api/prom/push"
    queue_config:
      capacity: 10000
      max_samples_per_send: 2000
Development

Custom Exporter Development

Building exporters in Go and Python

Python Example (Prometheus Client):

from prometheus_client import Counter, Histogram, start_http_server
import random

REQUESTS = Counter('app_requests_total', 'Total requests')
LATENCY = Histogram('app_latency_seconds', 'Request latency')

@LATENCY.time()
def process_request():
    REQUESTS.inc()
    time.sleep(random.random())

if __name__ == '__main__':
    start_http_server(8000)

Best Practices:

  • Always use namespaces for metrics (e.g., appname_requests_total)
  • Follow USE (Utilization/Saturation/Errors) for resources
  • Follow RED (Rate/Errors/Duration) for services
  • Never change label names in patch releases
Metrics Design

Histograms & Quantiles Deep Dive

Proper bucket configuration and statistical analysis

Bucket Strategy: Choose buckets based on your SLOs. If target latency is 100ms, use buckets around that value.

# Default buckets (suitable for web services)
.005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10

# Custom buckets for database queries
buckets=[.001, .005, .01, .025, .05, .1, .25, .5, 1]

Warning: histogram_quantile() is an approximation based on buckets. Error increases with fewer buckets. Use rate() before histogram_quantile().

Kubernetes

Prometheus Operator & CRDs

Native Kubernetes management of Prometheus instances

The Prometheus Operator introduces Kubernetes CRDs for managing Prometheus, Alertmanager, and related components declaratively.

# ServiceMonitor CRD
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: frontend
spec:
  selector:
    matchLabels:
      app: frontend
  endpoints:
  - port: web
    interval: 30s
    path: /metrics

Key CRDs:

  • Prometheus: Defines Prometheus deployment, storage, retention
  • Alertmanager: Configures Alertmanager clusters
  • ServiceMonitor: Declarative scraping specification
  • PodMonitor: For scraping pods directly
  • PrometheusRule: Alerting and recording rules
Architecture

Thanos Architecture

Global query view and unlimited retention

Sidecar Pattern: Thanos Sidecar runs alongside Prometheus, uploads blocks to object storage (S3/GCS), and provides gRPC API for Queriers.

Core Components:

  • Querier: Global query layer aggregating data from Sidecars and Store Gateways
  • Store Gateway: Serves historical data from object storage
  • Compactor: Downsampling and compaction of old blocks (5m → 1h → 1d resolution)
  • Ruler: Global recording/alerting rules across all clusters
  • Receiver: Accepts remote-write data (alternative to Sidecar)
# Query across all clusters
thanos query \
  --store=thanos-sidecar-1:10901 \
  --store=thanos-sidecar-2:10901 \
  --store=thanos-store:10901
Observability

OpenTelemetry Migration

Bridging Prometheus and modern observability standards

OTel Collector: Receives OTLP data and exports to Prometheus remote_write or OTLP.

receivers:
  otlp:
    protocols:
      grpc:
      http:
exporters:
  prometheusremotewrite:
    endpoint: http://cortex:9009/api/prom/push
service:
  pipelines:
    metrics:
      receivers: [otlp]
      exporters: [prometheusremotewrite]

Exemplars: Link metrics to traces using OTel exemplars. Prometheus supports exemplars in OpenMetrics format, allowing you to jump from a latency spike to the specific trace causing it.

Security

Security Hardening

TLS, mTLS, and RBAC implementation

Scrape TLS Configuration:

scrape_configs:
  - job_name: 'secure-app'
    scheme: https
    tls_config:
      ca_file: /etc/prometheus/certs/ca.crt
      cert_file: /etc/prometheus/certs/client.crt
      key_file: /etc/prometheus/certs/client.key
      insecure_skip_verify: false

Authentication Methods:

  • Basic Auth: Username/password in scrape_config
  • Bearer Token: For Kubernetes API and service mesh
  • OAuth2: Client credentials flow support
  • AWS SigV4: Native support for AMP (Amazon Managed Prometheus)

Network Security: Use reverse proxy (nginx/traefik) with basic auth for Prometheus UI, or enable --web.enable-admin-api with caution (allows snapshot creation and TSDB admin).

Why pull vs push architecture?

Architecture • Level 1

Advantages:

• Single source of truth (server config)
• Easy target health detection
• Works through firewalls/NAT
• Can test locally with curl

rate() vs irate()

PromQL • Level 2

rate(): Average per-second over time range (smooth, good for alerts)

irate(): Instant rate using last 2 points (spiky, good for graphs)

Handling high cardinality

Scaling • Level 3

• Drop labels via metric_relabel_configs
• Use recording rules to pre-aggregate
• Increase scrape interval
• Shard by job/target
• Move to Thanos/VictoriaMetrics

Counter vs Gauge

Architecture • Level 1

Counter: Cumulative, only increases (resets to 0). Use rate().

Gauge: Arbitrary values up/down. No aggregation needed.

Lookback delta (staleness)

PromQL • Level 3

Default is 5 minutes. If no sample in last 5m, time series is marked stale and won't appear in queries. Prevents old data from lingering after targets die.

Federation vs Thanos

Scaling • Level 4

Federation: Hierarchical, scrapes aggregated data from other Prometheus instances. Limited scale.

Thanos: Sidecar pattern with object storage, global query view, unlimited retention.
